## 3. Findings

### F1 — Blocker — Verified — Every real Nmap XML document is rejected, so no real scan or import can ever store a host

Evidence (real Nmap 7.993 on the only permitted target):

```
$ nmap -sT -p 22,80 127.0.0.1 -oX real.xml -oN real.txt
$ head -3 real.xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE nmaprun>
<?xml-stylesheet href="file:///usr/bin/../share/nmap/nmap.xsl" type="text/xsl"?>

$ lumos scan ./real.sqlite 127.0.0.1 --network local --nmap-options "-sT -p 22,80,443,8080" --yes
Nmap command: /usr/bin/nmap -sV -n -sT -p 22,80,443,8080 -oX - 127.0.0.1
XML parser: DTD or entity declaration is forbidden in Nmap XML
Scan 6e057ea6-…: failed; 0 host(s); exit 0

$ lumos import ./real.sqlite ./real.xml --network local
DTD or entity declaration is forbidden in Nmap XML
XML import : partial/failed; 0 host(s)
```

Cause: `src/lumos/core/nmap/xml_stream.py:14` rejects on the literal substrings `<!DOCTYPE`/`<!ENTITY` (`:247-249`). Nmap always emits `<!DOCTYPE nmaprun>`; there is no Nmap option that suppresses it (`--no-stylesheet` only removes the PI).

The suite cannot catch this because every fixture omits the DOCTYPE (`tests/fixtures/nmap/normal.xml` starts `<?xml version="1.0"?>` then `<nmaprun …>`), and `tests/test_xml_stream.py:37` (`test_dtd_and_entity_declarations_are_rejected`) actively asserts that Nmap's own header must be refused.

Why it matters: this is a broken fixed requirement ("Nmap is the user's own installed copy"; scans must store observations). A real scan writes a `failed` scan row with zero hosts and no topology, and the exit state is reported to the user as a parse error. The 214 green tests are green because they never feed the parser a byte of real Nmap output.

Suggested fix (not applied):

```diff
--- a/src/lumos/core/nmap/xml_stream.py
+++ b/src/lumos/core/nmap/xml_stream.py
@@
-_FORBIDDEN_DECLARATIONS = (b"<!DOCTYPE", b"<!ENTITY")
+# Nmap always emits `<!DOCTYPE nmaprun>`; only an internal subset (entity
+# declarations, which is how XXE is expressed) is unsafe.
+_ALLOWED_DOCTYPE = re.compile(rb'<!DOCTYPE\s+nmaprun\s*>', re.IGNORECASE)
+_FORBIDDEN_DECLARATIONS = (b"<!ENTITY", b"<!DOCTYPE")
@@ def parse_nmap_xml(...
-            probe = (tail + chunk).upper()
-            if any(token in probe for token in _FORBIDDEN_DECLARATIONS):
-                raise NmapXmlError("DTD or entity declaration is forbidden in Nmap XML")
-            tail = probe[-16:]
+            probe = _ALLOWED_DOCTYPE.sub(b"", tail + chunk).upper()
+            if b"<!DOCTYPE" in probe or b"<!ENTITY" in probe:
+                raise NmapXmlError("DTD or entity declaration is forbidden in Nmap XML")
+            tail = probe[-16:]
```

and replace `hostile-dtd.xml`'s assertion with a "banner-with-DOCTYPE-and-no-entities is accepted" test plus a committed, sanitized, real-Nmap fixture that includes the DOCTYPE. Keeping the DOCTYPE regex narrow (DOCTYPE exactly `nmaprun`, no internal subset) preserves the XXE protection that `_FORBIDDEN_DECLARATIONS` was aiming at.

### F2 — High — Verified — A partially parsed import crashes the CLI with a traceback instead of reporting the parse error

Evidence:

```
$ lumos import ./trunc.sqlite tests/fixtures/nmap/truncated.xml --network n
  File ".../src/lumos/services/actions.py", line 394, in run
    return _fail(f"imported {hosts} host(s) with errors", detail=parse_error, payload={"scan_id": scan_id})
TypeError: _fail() got an unexpected keyword argument 'payload'
exit=1
```

`_fail` (`src/lumos/services/actions.py:64`) takes only `message`/`detail`; the error path passes `payload`. The same fixture imports successfully via `import_nmap_xml`, so the hosts are written — the only broken thing is the reporting path, on exactly the input class the spec calls hostile ("truncated XML", "keeps completed hosts when possible"). In the TUI the same call is caught by `run_task` and shown as `import failed: _fail() got an unexpected keyword argument 'payload'`, i.e. the user never learns the real parse error.

Suggested fix: give `_fail` a `payload` keyword (`def _fail(message, *, detail="", payload=None): return ActionResult(False, message, detail, payload)`), and add a regression test that drives `actions.import_xml` with `truncated.xml` and asserts `not result.ok` and that `detail` contains "Truncated".

### F3 — High — Verified — Merge validates neither the source's schema version nor its columns, and drops unknown columns silently

Evidence (scratch copy, same-uid sources):

```
user_version=99 source: ACCEPTED {'networks': 1, ...}
extra-column source: ACCEPTED, rows= {'networks': 0, ...}   # ALTER TABLE networks ADD COLUMN secret_note
target columns: ['id','engagement_id','name','cidr','family','notes','created_at']   # secret_note gone
```

`src/lumos/core/merge.py:194-200` reads `PRAGMA application_id`/`user_version` only to put them in `merge_log`; acceptance is decided purely by `engagement_uid`. `_copy_rows` (`:141-143`) intersects the source's columns with the target's, so a source written by a newer schema merges "successfully" while every column the target does not know is discarded, and `INSERT OR IGNORE` hides same-id content conflicts. The plan's merge contract (lines 155-157) explicitly requires verifying application ID, supported `user_version`, `integrity_check`, the table/column set, and rejecting triggers/views/virtual tables, with `trusted_schema` off; none of that happens on the source connection.

Why it matters: silent data loss on the one operation whose purpose is not to lose data. Independent-file rejection and double-merge idempotence do work (verified: `merge twice inserted: 0 0`, and a different uid is rejected and logged `rejected`).

Suggested fix: before the uid comparison, run the source through the same identity/schema validation used for the target (`application_id`, `user_version == SCHEMA_VERSION`, expected table set, exact column set per table, no triggers/views/virtual tables), `PRAGMA trusted_schema=OFF` on the source, and refuse with a `MergeError` + `merge_log` row (`outcome='rejected'`, reason naming the mismatch) instead of silently narrowing columns.

### F4 — Medium — Verified — The curses thread performs unbounded database work, so the UI blocks for hundreds of milliseconds

Evidence: `flow_open_path` (`src/lumos/tui/flows.py:174`) calls `actions.open_engagement` directly on the UI thread; that runs `check_database` → `validate_database(integrity=True)` → `PRAGMA integrity_check` + `PRAGMA foreign_key_check` over the whole file (seconds on a large engagement, as `database.py:212-216` itself notes for the read path). `_run_event_loop` (`src/lumos/tui/app.py:311`) also calls `load_map_snapshot` on the UI thread at startup and after every command; measured 667 ms on the 100k benchmark database (§ numbers below). Every other long action correctly uses `run_task`'s worker thread, so this is an inconsistency rather than a design gap.

Why it matters: the spec's non-negotiable is "any operation that can take more than ~100 ms runs off the curses loop". Opening a 300 MB engagement currently freezes the interface without a progress panel, exactly where a user is most likely to press keys.

Suggested fix: run `open_engagement` through `run_task`, and move the initial/refresh `load_map_snapshot` to the watcher thread (publish the first snapshot the same way it publishes later ones).

### F5 — Medium — Verified — `rebuild_inferred` takes 25 s at 100k hosts, runs automatically after every scan/import, and is neither benchmarked nor tested at scale

Evidence (benchmark fixtures, Python 3.14.9, 8 CPUs):

```
hosts=10000   build=1.5s   rebuild_inferred=1.83s   hubs=40  edges=10040
hosts=100000  build=23.7s  rebuild_inferred=25.22s  hubs=400 edges=100400
```

`scanning.py:192-201` and `xml_import.py:154-161` call it inline at the end of every successful scan/import (worker thread in the TUI, so the interface stays live, but the operation the user is waiting on gains 25 s). No test or benchmark covers its cost; the scale benchmark stops at rendering.

Suggested fix: measure it in `bench/map_benchmark.py`, and either batch the per-host plan writes or make the automatic post-scan rebuild a background job with a visible "links not rebuilt yet" state.

### F6 — Medium — Verified — README describes a working Nmap pipeline that the code cannot deliver

The README's current-status section is unusually candid about what is missing (no ping-only mode, no notes editor, no real-scan numbers, Python 3.10 unverified), and those statements match the code. But three functional claims are contradicted by F1/F2:

- "It parses Nmap XML incrementally, keeps completed hosts when possible after truncated output" — truncated import raises `TypeError` (F2); real XML never parses at all (F1).
- The quick start (`lumos scan …`) and "the **scan** command displays the final Nmap command before execution" imply a usable real scan. The command is displayed correctly, then produces `failed; 0 host(s)` on every real target.
- "Use of the user's installed Nmap" / "built on Nmap" is true of argv construction, false of the result path.

Suggested fix: fix F1, then re-word or re-verify the README status paragraph against a real scan on a local target.

### F7 — Low — Verified — The real scan network is still in git history, and `build/` is untracked but not ignored

Evidence: `git log --oneline -S'192.0.2'` shows commit `1ee2ed5`, whose message states it replaced "the actual scan network" `192.0.2.0/24` and private dev subnets; `git log -p --all` still contains `192.0.2.0/24`, `192.0.2.14`, `198.51.100.0/24`, `198.18.0.0`, `10.0.0.0`. The HEAD tree is clean (only reserved ranges, locally administered MACs, `.example` names; no public IPs, no keys, no tokens). `git status` in the working tree shows `?? build/` (504 KB) and `.gitignore` covers `dist/`, `.build/` but not `build/`.

Why it matters: the hygiene rule is "no real or sensitive data tracked anywhere in history". RFC1918 addresses alone are low-sensitivity, but the commit itself labels them the actual scan network, which makes the exposure real for the engagement owner.

Suggested fix: add `build/` to `.gitignore`; if the addresses matter, rewrite history before any public release (a history rewrite is outside this review's permissions).

### F8 — Low — Verified — `tests/test_topology_identity.py` leaks SQLite connections

Evidence: `PYTHONPATH=../src python3.14 -W error -m unittest <module>` per test module; only `test_topology_identity` reports `7` `ResourceWarning: unclosed database` at interpreter shutdown (the full suite shows 4 "Exception ignored while finalizing database connection"). Runtime paths I exercised (`database`, `merge`, `scanning`, `xml_import`, `map_view`, `tui`, `actions`, reports, inference) produce none.

Why it matters: a leaking test helper teaches the wrong pattern and will become flaky once connection cleanup is enforced.

Suggested fix: use `contextlib.closing`/`addClassCleanup` for the helper's connections.

### F9 — Low — Verified — `imported` edges render as measured in reports, though they are not

Evidence:

```
classify('imported', 0.2)  -> observed   SVG dash = ''
classify('traceroute',0.2) -> observed   SVG dash = ''
```

`src/lumos/core/evidence.py:36-46` sends every unknown `edge_type` to `observed` (solid). The schema permits `'imported'` (`schema.py:230`), and `braille.py:26` gives it its own dotted pattern, so the TUI and the reports disagree about the same row. Nothing in the current code creates `imported` edges, so this is latent rather than a wrong map today.

Suggested fix: make `classify` explicit — `imported` → its own class or `alternate`, and raise/return `weak` for unknown types instead of defaulting to solid.

### F10 — Low — Likely — Writer failures inside the Nmap reader thread escape to stderr, and inference failures are swallowed with no trace

`src/lumos/core/nmap/runner.py:309-332`: `read_and_parse` only catches `NmapXmlError`; `on_host` (`ScanWriter.submit_host`) raises `ScanStoreError` when the writer thread has failed, which escapes the reader thread and prints a Python traceback to the process's stderr — inside the curses UI that lands on the alternate screen. Inferred from code; I did not force a writer failure.

`scanning.py:196-201` and `xml_import.py:154-161` wrap `rebuild_inferred` in `except Exception: pass`, so a broken rebuild leaves the map without inferred links and no audit/log entry anywhere.

Suggested fix: catch `Exception` in `read_and_parse`, record it as the parse error, and surface rebuild failures in `audit_events`/the activity log instead of discarding them.

### F11 — Low — Verified — Dead and duplicated code, and one silent preset fallback

`merge.py:84-90` `_count()` is never called. `xml_import.py:23` `_local_name` duplicates `xml_stream.py:76` `_tag`. `flows.py:183` keeps selection state in a module global `_SCOPE_STATE` (shared across forms and engagements). `actions.py:236` defaults `preset="discover"`, a name absent from `SCAN_PRESETS`, so an unknown preset silently becomes an empty option string (and therefore a `-sT` scan) instead of an error.

### F12 — Low — Verified — A malformed range is reported as a hostname problem

`parse_target("198.51.100.5-198.51.100.300")` → `ScopeDecision(allowed=False, reason="hostname is not explicitly allowlisted")`, because a failed IP-range parse falls through to hostname normalization (`scope.py:87-91`). It fails closed, but the operator is told to fix a hostname allowlist when the target is an invalid range.
